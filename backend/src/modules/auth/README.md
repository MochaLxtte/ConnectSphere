# Authentication and roles workstream

Ryan owns this directory and the authentication workstream: profile mapping, login/logout, session verification, and role middleware. Coordinate public request/response contracts with the other feature owners before implementing them.

Supabase Auth verifies email/password credentials. The backend verifies a Supabase access token and sets it directly as a HttpOnly session cookie, re-verifies that cookie on later requests, and resolves the Supabase user id through `app_users.supabase_user_id` to the application-owned profile and role. `POST /api/auth/login`, `GET /api/auth/me`, and `POST /api/auth/logout` are mounted by the normal server.

Supabase owns credentials. ConnectSphere owns the role: provision the `app_users` profile and its role before sign-in, linking it to the verified Supabase user's UUID through `supabase_user_id`. Login only looks up this mapping; an unmapped account receives `403 ACCOUNT_NOT_PROVISIONED` and no profile is created automatically.

Migration `004_add_supabase_user_id.sql` adds the nullable, unique UUID mapping for reproducible local and CI databases. Existing profiles remain unmapped until provisioned. Migration 003 is retained as historical schema; its Firebase identity table is not used by the Supabase implementation. The shared project's UUID mapping column, unique index and two test-account mappings were checked on 15 September. For any new environment, coordinate the equivalent schema with Arvin and provision the account mappings with Ryan before testing login.

Configure matching `SUPABASE_URL` on the backend and `VITE_SUPABASE_URL` plus `VITE_SUPABASE_ANON_KEY` for the frontend. `VITE_SUPABASE_ANON_KEY` accepts the project's publishable key despite the variable's legacy name. The optional backend-only `SUPABASE_JWT_SECRET` is needed only for legacy HS256 signing; otherwise the verifier uses the project's JWKS. The current shared project uses asymmetric ES256 keys, so leave that secret blank. Never put a signing secret or privileged Supabase key in a `VITE_*` variable.

The browser SDK only performs the sign-in exchange; it does not persist a second application session. The Express cookie expires with the verified token, subject to the server's maximum lifetime. Automatic token refresh is not implemented, so an expired session requires sign-in again. Logout clears this browser's application cookie; it does not revoke every token or another device's session.

`server.ts` starts `createRuntimeApp` from `backend/src/runtime-app.ts`, which supplies the same Supabase session verifier to authentication and event routes. The normal server mounts event listing, shared detail, draft editing, submission and approval/rejection. Organisers retain access to their own requests; only the currently assigned coordinator can access a request through the coordinator queue, detail or review workflow. Coordinators cannot view drafts, and initial decisions still require `SUBMITTED` status with no recorded decision.

Assignment compares `event_requests.coordinator_id` with the verified `app_users.id`, not the Supabase UUID. Null or different assignments deny coordinator access. The decision write rechecks assignment against the locked event row. This is the Sprint 1 team implementation assumption; customer clarification about unassigned triage and delegation remains open in [Q-02](../../../../docs/requirements/assumptions-and-questions.md). Until the KAN-29 assignment workflow is implemented, assign synthetic test requests through the Supabase dashboard after provisioning the mapped application profiles.

The coordinator review page consumes the shared decision action flag and displays saved outcomes independently of permission to make a new decision. It reloads the shared detail after saving. On 15 September, sign-in and a manual webpage approval succeeded, with the synthetic request's status observed changing from `SUBMITTED` to `APPROVED` in Supabase. This does not complete the hosted rejection, reload/reason, queue-removal, unauthorised-access or organiser-workflow checks. Organiser pages and the list API's draft-only restriction still need KAN-16 work. See [test evidence](../../../../docs/testing/test-evidence.md).

Always verify the caller on the server and enforce role and resource ownership from that verified identity, never from client input. Never serialize a database row containing `password_hash`.
