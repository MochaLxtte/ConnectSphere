Ryan owns this directory and the authentication workstream: profile mapping, login/logout, session verification, and role middleware. Coordinate public request/response contracts with the other feature owners before implementing them.

Supabase Auth verifies email/password credentials. The backend verifies a Supabase access token and sets it directly as a HttpOnly session cookie, re-verifies that cookie on later requests, and resolves the Supabase user id through `app_users.supabase_user_id` to the application-owned profile and role. `POST /api/auth/login`, `GET /api/auth/me`, and `POST /api/auth/logout` are mounted by the normal server.

Supabase owns credentials. ConnectSphere owns the role: provision the `app_users` profile and its role before sign-in, linking it to the verified Supabase user's UUID through `supabase_user_id`. Login only looks up this mapping; an unmapped account receives `403 ACCOUNT_NOT_PROVISIONED` and no profile is created automatically.

Migration `003_add_supabase_user_id.sql` adds the nullable, unique UUID mapping for reproducible local and CI databases. Existing profiles remain unmapped until provisioned. Firebase migration 003 was retired from the active migration files on 30 September. Its old database history, table and data are preserved where present; fresh databases no longer create that unused table. Supabase authentication does not read it. The shared project's UUID mapping column, unique index and two test-account mappings were checked on 15 September. For any new environment, coordinate the equivalent schema with Arvin and provision the account mappings with Ryan before testing login.

Configure matching `SUPABASE_URL` on the backend and `VITE_SUPABASE_URL` plus `VITE_SUPABASE_ANON_KEY` for the frontend. `VITE_SUPABASE_ANON_KEY` accepts the project's publishable key despite the variable's legacy name. The optional backend-only `SUPABASE_JWT_SECRET` is needed only for legacy HS256 signing; otherwise the verifier uses the project's JWKS. The current shared project uses asymmetric ES256 keys, so leave that secret blank. Never put a signing secret or privileged Supabase key in a `VITE_*` variable.

The browser SDK only performs the sign-in exchange; it does not persist a second application session. The Express cookie expires with the verified token, subject to the server's maximum lifetime. Automatic token refresh is not implemented, so an expired session requires sign-in again. Logout clears this browser's application cookie; it does not revoke every token or another device's session.

`server.ts` starts `createRuntimeApp` from `backend/src/runtime-app.ts`, which supplies the same Supabase session verifier to authentication and event routes. The normal server mounts event listing, shared detail, draft editing, submission and approval/rejection. Organisers retain access to their own requests; only the currently assigned coordinator can access a request through the coordinator queue, detail or review workflow. Coordinators cannot view drafts, and initial decisions require `SUBMITTED` or `UNDER_REVIEW` status with no recorded decision.

Assignment compares `event_requests.coordinator_id` with the verified `app_users.id`, not the Supabase UUID. Null or different assignments deny coordinator access. The decision write rechecks assignment against the locked event row. The [CR-5 customer change](../../../../docs/requirements/change-requests.md) replaces the earlier unassigned-triage policy with trusted Lead allocation. KAN-65 implements versioned Lead reassignment with retained history and immediate access transfer; dated rollout notes below retain their original checkpoints.

## KAN-79 trusted Lead access — 19 October 2026

Migration [007](../../../../database/migrations/007_add_coordinator_lead.sql) adds `EVENT_COORDINATOR_LEAD` to the application role constraint without changing existing users or assignments. Provision a real Supabase Auth account and link its UUID to a trusted `app_users` profile with that role. Ordinary users cannot create or promote application profiles: login accepts only `accessToken`, and the role comes from the mapped database profile, never browser input, headers or Supabase user metadata. Every authenticated request resolves the current profile again, so a changed role is used on the next request.

All Leads share the deployment's submitted/unassigned queue and active-event oversight. Lead-only endpoints are `GET /api/events/unassigned`, `/coordinators`, `/oversight`, `/oversight/:id` and `PUT /api/events/:id/coordinator`. Lead history reads are restricted to active events. Ordinary coordinators cannot use the older unassigned or allocation APIs to assign themselves work. The shared event-detail, review, clarification, venue and roster permissions are not broadened by the Lead role.

Submission now leaves a valid request `SUBMITTED` with no coordinator, even when no coordinator is available. Initial allocation requires an `EVENT_COORDINATOR` profile explicitly marked `coordinator_available = true`; the selected profile is locked and rechecked during the write. Availability controls future Lead selection, not login, session state or access to an existing assignment. The initial assignment records the Lead's application ID and retains automatic historical rows. KAN-65 reassignment and KAN-64 notifications are separate dependencies, with integration acceptance still pending.

Coordinate migration 007, mapped Lead provisioning and the frontend/backend rollout together using the [deployment sequence](../../../../database/README.md#kan-79-lead-assignment-rollout). No shared Supabase application of migration 007 or hosted Lead acceptance is claimed here.
