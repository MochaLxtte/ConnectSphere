# Event proposal workstream

Ernest owns event creation and draft saving; Kai Jie owns draft editing and submission. Irfan owns coordinator review and clarification; Tristan owns approval/rejection and organiser-facing status. These workstreams share this directory, with Arvin supporting database setup and cross-feature integration. Coordinate the field names in `types.ts` with the frontend event forms and database migrations before changing a contract.

The normal server exposes organiser lists, shared request details, owned-draft updates and submission, the assigned coordinator's review queue, and approval/rejection. For organisers, `GET /api/events` preserves the own-draft list; `GET /api/events?scope=all` includes all of their request statuses, newest update first, and supplies the organiser page at `/events`. The shared detail GET returns `review` and caller-specific `actions` alongside the event fields. The coordinator interface consumes these fields, and KAN-16's request titles link to a read-only organiser view at `/events/:id` using the same GET. It displays status and any recorded outcome, reason and time without exposing write controls. No additional handler or schema change is needed for this view. Hosted organiser checks cover outcome display/refresh, signed-out detail access, Draft/Submitted detail states and another organiser's denied detail access and empty list (MAN-20260917-01 through MAN-20260917-04). Remaining list/status/refresh, signed-out list and submission checks are in [test evidence](../../../../docs/testing/test-evidence.md).

`submitted-requests-router.ts` owns the shared GET, draft PATCH and submit routes; `review-router.ts` owns decision writes. Services validate runtime input, enforce ownership/assignment and lock rows during state changes. Review creation and the matching status update commit together. TypeScript interfaces do not validate untrusted HTTP input. Preserve parameterized queries, server-derived identity and transaction boundaries when adding features; preserve `false` and `0` as values when handling nullable fields.

The schema supports `DRAFT`, `SUBMITTED`, `UNDER_REVIEW`, `CLARIFICATION_REQUESTED`, `APPROVED` and `REJECTED`. Implemented transitions are `DRAFT` → `SUBMITTED` and `SUBMITTED` → `APPROVED`/`REJECTED`; intermediate-state transitions and clarification handling remain pending. An existing decision prevents another initial decision. Decided requests leave the queue but remain readable to the owning organiser and currently assigned coordinator.

Creating and saving a new draft, clarification and the coordinator assignment workflow are not implemented here yet; updating an existing draft is supported. All editable fields allow `null` for incomplete drafts. Submission currently requires `name`, `purpose`, `startsAt`, `endsAt`, `expectedAttendance` and `venueRequirements` under the team's provisional rule; customer clarification remains open. Initial decisions permit an optional reason. Assignment requires `coordinator_id` to match the verified coordinator's application ID; synthetic requests can be assigned through the Supabase dashboard until KAN-29 is implemented.

See the [API contract](../../../../docs/architecture/api-contract.md) and [decision log](../../../../docs/requirements/assumptions-and-questions.md) before changing these rules. Add a migration if the stored vocabulary changes. Future venue, equipment, attendance and scheduling work should have their own modules as those stories enter a sprint.
