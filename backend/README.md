Express 5, TypeScript, and Supabase PostgreSQL on Node.js 24. Run dependency installation and database setup from the repository root using the root README, then run `npm run dev --workspace @connectsphere/backend`. `npm run build --workspace @connectsphere/backend` produces `dist/`; `npm run start --workspace @connectsphere/backend` starts that build.

`src/config/env.ts` loads the repository root `.env` in both source and compiled execution, regardless of the shell's working directory. Existing environment variables take precedence. `DATABASE_URL` is required at server startup; `API_PORT` defaults to `3000`, `API_HOST` to `127.0.0.1`, and `NODE_ENV` to `development`. Bind to `0.0.0.0` explicitly when a container or another machine must reach the API.

The API connects to Supabase through `pg`; event data continues to pass through Express. Configure `DATABASE_URL` with `sslmode=verify-full` and disable the unused Data API as described in [database setup](../database/README.md). The optional `MIGRATION_DATABASE_URL` is used only by migrations and seeds. No Supabase API key is needed for this SQL connection. Supabase Auth handles sign-in; Express verifies its tokens using `SUPABASE_URL` and maps the subject to `app_users.supabase_user_id`. See [authentication setup](src/modules/auth/README.md).

The [API contract](../docs/architecture/api-contract.md) defines current role, state and error responses.

Unknown endpoints return a JSON `NOT_FOUND` error with HTTP 404. Malformed JSON returns `INVALID_JSON`/400, JSON bodies above 100kb return `PAYLOAD_TOO_LARGE`/413, and unexpected failures return `INTERNAL_ERROR`/500. Client responses omit stacks and database connection details. Helmet adds default security headers. The API intentionally has no permissive CORS policy; the frontend development proxy and a same-origin production reverse proxy can route `/api` requests.

## KAN-9 read-only equipment checks

`createRuntimeApp` mounts the equipment router with the existing verified session and shared PostgreSQL pool. Only `TECHNICAL_SUPPORT_STAFF` may call it; Lead or venue-calendar access does not grant equipment-check access. Each assessment reads eligible event fields, saved requirements, current stock and overlapping reserved quantities in one SQL statement snapshot, checks the source version, then returns advisory quantities without writes. Unknown/invalid inputs fail explicitly; a missing saved requirement never produces a green result.

## KAN-26 saved equipment reservation writes

The reservation router is mounted at `/api/equipment/reservations` with the same verified Technical Support role, minimal event projection and no-store responses. The context reads approved/confirmed events; mutations require an approved event and a full saved line. Reserve accepts only a source version; cancel additionally requires a trimmed 1–2,000-character reason. `CONFIRMED` is read-only. Both mutations return `{ changed, context }`; exact repeats are no-ops, while stale sources fail with a conflict. No request-creation, partial-quantity or unsaved what-if mutation endpoint is exposed.

Writes lock the trusted Technical Support profile, event, assigned coordinator profile for reserve, ordered equipment pools and ordered saved lines before reading current operational capacity. A new reservation requires the assigned profile to retain the Event Coordinator role. The transaction includes notifications for the current coordinator and acting Technical Support user. Migration 015 protects database writes too, retains allocation/decision/release history and releases live reservations once on cancelled/completed event transitions. Stock losses retain existing reservations and appear as a readiness shortfall. KAN-62/KAN-10 event lifecycle APIs and remaining KAN-80 triggers are separate pending work. [The reservation contract](../docs/architecture/api-contract.md#equipment-reservations-kan-26-cf-17) documents exact responses and errors.

## Team extension points

- `src/app.ts`: app composition, health endpoints, and error responses. Tests can inject a database without opening a real connection.
- `src/runtime-app.ts`: normal-server wiring for the shared session verifier and explicit coordinator access policies; integration tests use the same composition.
- `src/server.ts`: environment loading, listener startup, and graceful shutdown.
- `src/db/pool.ts`: one shared PostgreSQL pool with bounded connection/query timeouts.
- `src/modules/auth/`: Supabase token verification, application-user mapping, session routes and seven role contracts, including Coordinator Lead and Safety Officer.
- `src/modules/events/`: draft editing/submission, queue and shared detail, decision validation, Lead assignment/reassignment, access policies and transactional persistence.
- `src/modules/venues/`: KAN-12 search, KAN-51 availability, KAN-52 suitability, KAN-53 booking submission, KAN-8 decisions, KAN-55 operational blocks, KAN-50 catalogue and KAN-77 buffer settings, using `workflowRoute` for verified sessions, role gates and error mapping. See the [venue module](src/modules/venues/README.md) for transactional decision rules.
- `src/modules/equipment/`: KAN-9 input validation, microsecond-aware availability rules and KAN-26 saved-reservation context/writes. [Module contract](src/modules/equipment/README.md); migration 014 supports availability and 015 supports reservations.
- `src/modules/notifications/`: recipient-scoped inbox and read state, trigger/recipient mapping and same-transaction outcome writes.

Organisers can read their own requests; coordinators can read non-drafts assigned to their `app_users.id`. Leads have separate allocation and oversight endpoints for `SUBMITTED`, `UNDER_REVIEW`, `CLARIFICATION_REQUESTED`, `APPROVED` and `CONFIRMED` events. A Lead is not an Event Coordinator for shared-detail, review, venue or roster permissions. Initial event approval/rejection requires `SUBMITTED` or `UNDER_REVIEW` status with no recorded decision. The write rechecks assignment and state against a locked row. Venue booking decisions are separate: only Venue Staff may write, and only a `PENDING` booking can change to `APPROVED` or `REJECTED`. Approval requires an `APPROVED` event and active venue; rejection can close a stale pending request. Keep server checks when extending routes; frontend flags are only presentation guidance.

Run `npm run typecheck --workspace @connectsphere/backend`, `npm test --workspace @connectsphere/backend`, and `npm run test:coverage --workspace @connectsphere/backend` from the root. These suites combine isolated rules with HTTP integration using substituted services, and real JOSE verification against a loopback JWKS fixture. `npm run test:integration` uses dedicated PostgreSQL to test migrations, persistence, authentication mappings and composed routes. `npm run test:coverage:backend` runs both sets together and measures the same owned backend source, including runtime constants in `types.ts`. It excludes only the process entry point, which the isolated browser harness starts normally. Neither database command uses the shared Supabase project. [Coverage gates and exceptions](../docs/testing/README.md#coverage-gates-and-remaining-exceptions--1-november-2026) and [run evidence](../docs/testing/test-evidence.md) distinguish isolated, combined and connected acceptance results.
