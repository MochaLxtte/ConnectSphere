## How the registers join

1. Read the feature or change, find its parent story, and identify the version of the AC in the relevant sprint card. Original assignment, notification and venue rules changed over time. [Sprint 1](../scrum/sprint-01/sprint-backlog.md) · [Sprint 2](../scrum/sprint-02/sprint-backlog.md) · [Sprint 3](../scrum/sprint-03/sprint-backlog.md) · [Sprint 4](../scrum/sprint-04/sprint-backlog.md)
2. Use the full specification ID in the case register. It identifies the scenario, preconditions, data, steps and expected result. The trace register groups cases, source files and test files at different levels of detail. Use the AC and behavior to choose the relevant file within a grouped row. Sprint test-group labels such as `S4-T15` are not execution IDs.
3. Join the case ID to **all** execution rows. Read the build, environment, actual outcome and evidence of the particular attempt. A manual run can have a related automated test file. The named file does not turn a manual observation into an automated result, or vice versa.
4. Use the point-in-time outcome and the recorded retest together. A preparation placeholder, historical feature summary, broad journey, sprint review and formal release decision answer different questions.
