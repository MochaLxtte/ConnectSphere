# Requirements and release scope

The Week 1 customer described organisers coordinating events across separate records, conversations and staff roles. The Week 4 project instructions selected 20 core features from that wider brief. This index follows the work from an organiser’s first request to the staff and attendees who act on it. The [master register](product-backlog.md) gives each retained item’s estimate and review outcome. The [story cards](story-cards.md) connect those items to their detailed criteria. [Workbook and Folder 1 evidence guide](../submission/1/README.md)

## Release scope

The team retained **42 parent items / 174 SP**. The [six Week 7 changes](change-requests.md), received on 2 October, added seven new stories worth 47 SP to the 127 SP of original-scope work. The latter includes the shared database/integration item. At [planning on 4 October](../scrum/sprint-03/evidence/meetings/current/planning.docx), the team selected 63 SP for Sprint 3 and forecast 63 SP for Sprint 4. Four items archived on 21 September are identified separately in the master register. The four reviews accepted **24, 24, 63 and 63 SP**. The [release accounting](../scrum/release-burndown.md) distinguishes the full-point carry-overs from new scope. The [frozen-release decision](../submission/release-record.md#release-decision) records the separate product-level decision.

## Connected workflows

An organiser can save an incomplete draft, but submission requires enough information for review. Before Week 7 the system automatically selected a coordinator. CR-5 sends new submissions to a Lead for allocation. Approval of the request starts planning. When venues and equipment are ready, the event can be confirmed. Starting preparation also requires a current Safety Officer approval. A safety-relevant change invalidates that approval, even if earlier values are later restored.
